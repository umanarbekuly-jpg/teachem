# Управление пользователями TeachEm

Вход: `http://localhost:8080/login`. Панель: `http://localhost:8080/admin/users`.
Роль в API и БД — `SUPERADMIN`; адрес кабинета `/admin` сохранён.

## Инварианты и данные

- Миграция `202610200001_superadmin` переименовывает роль существующего администратора, сохраняя его ID и связи. При нескольких администраторах миграция останавливается до выбора владельца.
- Частичный уникальный индекс запрещает второго суперадминистратора даже при параллельных запросах. Триггеры запрещают удаление, понижение роли, замену ID и TRUNCATE пользователей; ограничение CHECK запрещает блокировку и мягкое удаление суперадминистратора. Отложенный триггер проверяет наличие ровно одного владельца при изменении пользователей.
- На пустой установке сначала выполняется seed: первая запись пользователя должна быть суперадминистратором. Seed ищет владельца по роли, не обновляет его пароль или логин и не создаёт новый аккаунт из-за изменения `ADMIN_EMAIL`.
- `supadmin@teachem` разрешён только как логин владельца. Исключение формата есть только в форме входа и LoginDto. Регистрация и создание/редактирование обычных пользователей требуют полноценный email. Уникальность email проверяется без учёта регистра.
- Добавлены фамилия, телефон, общее описание и фото, состояние подтверждения email, признак обязательной смены пароля и версия авторизации. Поля тьютора переиспользуются из `TutorProfile`; отдельной системы аккаунтов нет.
- Смена email снимает подтверждение и завершает сессии. Отправка писем подтверждения пока не реализована; панель честно показывает отсутствие подтверждения.
- Смена роли не удаляет профиль, курсы, занятия, оплаты и историю. Активный оплаченный доступ студента, опубликованные курсы тьютора, будущие занятия или действующий доступ его учеников блокируют смену роли с объяснением.
- Версия авторизации и отзыв сессий прекращают доступ по прежним токенам. Создание новой сессии проверяет версию в транзакции, поэтому вход, начавшийся до сброса пароля, не восстанавливает старые права.
- Назначенный пароль хранится только в виде bcrypt-хеша с cost 12. Пользователь сначала вводит назначенный пароль и выбирает свой в `/change-password`; до этого остальные защищённые API закрыты. `/auth/me` доступен для определения необходимого экрана, а `/auth/logout` — для выхода. Смена собственного пароля требует текущего пароля, в том числе для суперадминистратора.
- Журнал хранит автора, целевой ID, время, тип действия и названия изменённых полей. Пароли, хеши, токены и содержимое профиля в журнал не попадают.

## Запуск на Windows

Откройте Docker Desktop, затем PowerShell в папке проекта:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

Скрипт пересобирает изменившиеся образы, применяет миграции через Compose, ждёт готовности и открывает вход. Он не меняет установленный пароль.

Остановка с сохранением данных: `docker compose stop`. Не используйте `down -v`.
После обновления исходников нужен `docker compose up -d --build --wait`, одного обновления страницы недостаточно.

## Проверки

`pnpm test` проверяет доменные правила и безопасность. `pnpm test:e2e` требует отдельную БД с `test` в URL и применённые миграции. Новый набор проверяет создание обеих ролей, первый вход, сохранение профиля и фото, email, смену роли, отзыв access/refresh, сброс и обязательную замену пароля, права API, запреты БД, одновременные вставки и аудит. Лимит частоты запросов заменяется только в новом тестовом наборе, чтобы многократные входы не мешали проверке сценариев.

## Резервная копия и откат

До обновления рабочей БД выполнены `pg_dump -Fc` и пробное восстановление в отдельную БД. Копии содержат персональные данные и хеши; храните их вне Git.

Сервер и интерфейс откатывайте согласованно: прежний интерфейс не знает роль SUPERADMIN и сценарий обязательной смены пароля. Сначала остановите API и web. Не запускайте старый API с новой схемой: роль была переименована.

1. Сохраните свежий дамп текущей БД и не удаляйте volumes MinIO. Это сохранит изменения, сделанные после обновления.
2. Восстановите **дамп до обновления в новую отдельную базу**, используя `createdb` и `pg_restore --no-owner --exit-on-error -d <новая_база> <дамп>`. Не применяйте `--clean` к рабочей БД.
3. Проверьте пользователей, курсы и оплаты в восстановленной базе. Данные после даты дампа останутся в сохранённой текущей базе и свежем дампе; перед переключением согласуйте их перенос. Простое восстановление старого дампа само по себе их не переносит.
4. Выполните `git revert` коммитов доработки в обратном порядке и пересоберите образы. В отдельном Compose override укажите восстановленную БД в `DATABASE_URL` для `migrate`, `seed` и `api`.
5. Запустите сервисы, проверьте вход и основные сценарии. В старой копии будут прежние логин и хеш пароля; новый пароль автоматически туда не переносится.

Текущая база остаётся доступной для возврата: не удаляйте её, дампы и файлы до завершения проверки. Откат кода не является восстановлением базы.
